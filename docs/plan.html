기획안 · LangChain Multi-agent Patterns

복합 의도 병렬 처리와 후속 질문 유도형 대화 에이전트

사용자가 한 문장에 여러 요청을 섞어 말해도 맥락을 잃지 않고 병렬로 처리합니다. 남은 빈칸과 확인이 필요한 일은 후속 질문으로 이어 갑니다. LangGraph와 MCP를 기반으로 하며, 커머스 도메인을 예시로 들었습니다.

01개요

예시 입력: “아까 물어본 후드티 결제하고, 아참 배송지 변경도 지금 돼?”

이 한 문장에는 결제(실행)와 배송지 변경(문의 또는 실행)이 섞여 있습니다. “아까 그 후드티”라는 이전 대화 맥락도 들어 있습니다. 이 시스템이 할 일은 세 가지입니다.

  1. 의도를 여러 개로 나누고, 각 의도가 실행인지 문의인지 구분합니다.
  2. 서로 독립적인 일은 병렬로, 선후관계가 있는 일은 순서대로 처리합니다.
  3. 남은 빈칸, 확인이 필요한 일, 다음 단계를 후속 질문으로 제시해 대화를 끝까지 이어 갑니다.

후속 질문은 답변 끝에 붙이는 장식이 아닙니다. 대화 스택에 남은 빈칸, 확인이 필요한 일, 다음 단계에서 계산해 내는 결과물입니다.

02복합 의도의 함정

두 의도로 나눠 곧바로 동시에 실행하면 사고가 날 수 있습니다.

함정설명대응
행동이냐 문의냐“변경도 지금 돼?”는 바꿔 달라는 요청일 수도, 가능한지 묻는 질문일 수도 있음의도마다 mode: action | inquiry를 붙여 추출
의존성이번 주문의 배송지라면 주소를 먼저 확정해야 결제할 수 있음할 일 사이를 DAG(선후관계 그래프)로 관리. 독립적인 일만 병렬 실행
되돌릴 수 없음결제는 취소가 어려움결제 직전에 interrupt로 사용자 확인(HITL)
모호함이번 주문 배송지인지, 기본 배송지인지 불분명함슬롯 채우기 후속 질문

LangChain 문서의 5가지 패턴에 대응시킨 결과입니다. 바깥 틀은 Custom workflow, 핵심은 Router입니다.

05상태 스키마

class Task(TypedDict):
    id: str
    intent: str                   # order_product, change_shipping_address ...
    mode: Literal["action", "inquiry"]
    slots: dict                   # 채워진 엔티티
    missing: list[str]            # 비어 있는 필수 슬롯
    depends_on: list[str]
    risk: Literal["low", "high"]  # high = 결제·취소 → HITL 필요
    status: Literal["pending", "blocked", "awaiting_confirm",
                    "running", "done", "failed"]
    result: dict | None

class FollowUp(TypedDict):
    label: str                    # 칩에 보일 문구
    type: Literal["slot", "confirm", "convert", "next", "recover"]
    payload: dict                 # 칩을 누르면 그래프로 다시 들어가는 구조화된 명령

class State(TypedDict):
    messages: Annotated[list, add_messages]
    task_stack: Annotated[list[Task], merge_by_id]   # 턴이 바뀌어도 유지, 병렬 갱신에 안전
    entity_memory: dict           # 최근 엔티티 (지시어 해석용)
    followups: list[FollowUp]

06Follow-ups 분류

유형생성 조건예시생성 방식
E 복구status = failed“카드 승인이 거절됐어요. 다른 결제수단으로 할까요?”규칙
B 실행 확인risk = high, awaiting_confirm“후드티 L / 블랙, 39,000원을 결제할까요?”규칙
A 슬롯 채우기missing이 비어 있지 않음“이번 주문 배송지를 바꿀까요, 기본 배송지를 바꿀까요?”규칙
C 문의→행동 전환inquiry의 답이 “가능함”“지금 변경 가능해요. 바로 바꿔 드릴까요?”LLM
D 다음 단계status = done“배송 추적 알림 받으실래요?”LLM

노출 규칙

  • 우선순위는 E > B > A > C > D이고, 한 번에 최대 3개까지 보여 줍니다.
  • 막힌 일(A·B·E)이 있으면 D 유형은 숨깁니다. 사용자의 주의를 막힌 일에 모으기 위해서입니다.
  • A·B·E는 반드시 나와야 하는 질문이라 LLM에 맡기지 않고 규칙으로 만듭니다.
  • 칩을 누르면 자연어가 아니라 payload로 그래프에 다시 들어갑니다. 의도를 다시 추출하는 비용과 오분류를 함께 줄일 수 있습니다.

08Subagents 적용 지점

Router는 분류하는 순간에 계획이 정해지고, Subagents는 중간 결과를 본 뒤에 다음 계획이 정해집니다.

단순 실행형 의도(결제, 주소 변경)에 Subagents를 쓰면 요청마다 호출이 1회 늘어 손해입니다(문서 기준 4회 대 3회). 아래 세 신호 가운데 하나라도 해당할 때만 씁니다.

신호의미
① 동적인 다단계 처리앞 단계 결과를 보고 나서야 다음에 누구를 부를지 정해짐
② 컨텍스트 격리하위 작업이 큰 컨텍스트(약관 전문, 리뷰 수백 건)를 소비하는데 메인에는 결론만 필요함
③ 하위 작업 자체가 에이전트 루프도구 호출이 3회 이상이고 그 순서를 스스로 판단해야 함

교환·환불 의사결정

신호 ① ②

“사이즈 안 맞는데 교환이 나아 환불이 나아? 쿠폰은?” 주문 조회 결과를 보고 정책 확인을, 정책 결과를 보고 금액 비교를 할지 정합니다. 약관 20K 토큰은 policy_agent 안에서만 소비하고 결론 한 줄만 올립니다.

조건부 상품 비교

신호 ② ③ · 동적 병렬

“영하 5도 패딩, 10만 원 이하 3개 비교.” 후보 수는 검색 결과를 봐야 알 수 있습니다. 후보마다 review_agent가 리뷰 300건을 분석해 요약만 반환합니다.

배송 사고 조사

신호 ① ③

“배송 완료인데 안 왔어요.” 택배사 API, GPS·사진, 창고 WMS, 이웃 배송 이력을 차례로 확인합니다. 몇 단계에서 끝날지 미리 알 수 없는 조사 루프입니다.

팀별 에이전트 소유

분산 개발 (문서 평가 5점)

결제팀, 물류팀, CS팀이 각자 에이전트를 배포합니다. 메인 에이전트와의 경계는 도구 계약(입력/출력 스키마) 하나로 좁혀집니다.

Subagents와 Follow-ups를 함께 쓸 때

문서 평가에서 Subagents의 사용자 직접 상호작용은 1점입니다. subagent는 사용자에게 직접 묻지 못합니다. 그래서 질문과 위험한 실행을 직접 하지 않고, 결과 객체에 담아 반환만 합니다.

class SubagentResult(BaseModel):
    summary: str
    data: dict
    needs_input: list[str] = []        # 물어볼 것 → main → followup_generator
    proposed_actions: list[dict] = []  # 실행 제안 → main이 위험도 판단 후 interrupt
원칙질문과 확인은 항상 메인 그래프의 followup_generator와 interrupt가 맡습니다. 그래야 사용자 경험과 안전장치가 한곳에서 일관되게 관리됩니다.

09구현 골격

from langgraph.graph import StateGraph, START, END
from langgraph.types import Send, interrupt
from langchain_mcp_adapters.client import MultiServerMCPClient
from langchain.agents import create_agent
from langchain.tools import tool

mcp = MultiServerMCPClient({
    "payment": {"url": "http://payment-mcp/mcp", "transport": "streamable_http"},
    "member":  {"url": "http://member-mcp/mcp",  "transport": "streamable_http"},
})

SUPERVISED = {"exchange_or_refund", "delivery_incident", "product_compare"}

def fan_out(state):
    ready = [t for t in state["task_stack"]
             if t["status"] == "pending" and deps_done(t, state)]
    if not ready:
        return "aggregator"
    return [Send("supervisor_agent" if t["intent"] in SUPERVISED else "simple_worker",
                 {"task": t}) for t in ready]

async def simple_worker(payload):
    task = payload["task"]
    if task["risk"] == "high":
        ok = interrupt({"type": "confirm", "task": task})   # 사용자 확인 대기
        if not ok:
            return {"task_stack": [cancel(task)]}
    tools = await tools_for(task["intent"])                  # 동적 도구 바인딩
    ...  # idempotency_key=task["id"]

# Subagents: 판단·조사형 의도 전용
policy_agent = create_agent(model, tools=policy_rag_tools, system_prompt="약관 해석 전문가 ...")

@tool
def ask_policy(question: str) -> str:
    """반품·교환·쿠폰 약관 해석. 결론과 근거 조항만 반환."""
    r = policy_agent.invoke({"messages": [{"role": "user", "content": question}]})
    return r["messages"][-1].content       # 격리: 최종 답만 메인으로 올림

supervisor = create_agent(model, tools=[ask_order, ask_policy, ask_pricing],
                          response_format=SubagentResult)

g = StateGraph(State)
for name, fn in [("intent_extractor", extract), ("stack_merger", merge),
                 ("planner", plan), ("simple_worker", simple_worker),
                 ("supervisor_agent", run_supervisor), ("aggregator", aggregate),
                 ("followup_generator", gen_followups)]:
    g.add_node(name, fn)
g.add_conditional_edges(START, entry_route, ["intent_extractor", "stack_merger"])  # 칩 payload면 추출 생략
g.add_edge("intent_extractor", "stack_merger")
g.add_edge("stack_merger", "planner")
g.add_conditional_edges("planner", fan_out,
                        ["simple_worker", "supervisor_agent", "aggregator"])
g.add_edge("simple_worker", "aggregator")
g.add_edge("supervisor_agent", "aggregator")
g.add_edge("aggregator", "followup_generator")
g.add_edge("followup_generator", END)
app = g.compile(checkpointer=PostgresSaver(...))   # 턴 사이에 스택 유지, interrupt 재개

구현 포인트

  • 동적 컨텍스트: 의도에 맞는 MCP 서버의 도구만 LLM에 바인딩합니다. 도구가 많아질수록 오호출이 줄어드는 효과가 큽니다.
  • 병렬 갱신: worker들이 동시에 task_stack을 갱신하므로 id 기준으로 merge하는 커스텀 reducer가 필요합니다.
  • 멱등성: 결제 도구에는 idempotency_key=task.id를 넘깁니다. 재시도나 interrupt 재개 때 이중 결제를 막습니다.
